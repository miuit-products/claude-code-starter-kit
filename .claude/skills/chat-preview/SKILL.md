# chat-preview

チャットで説明した内容（計画・比較・進捗・調査結果・アーキテクチャ・UI変更等）を、**ブラウザで開ける1枚の HTML 図解**にして見せるスキル。長い散文や関数名だらけの説明は読みづらい——要点と図に落として、ユーザーが一目で理解できるようにするのが目的。

**正本はこの1本**（`~/.claude/skills/chat-preview/`）。Codex は `~/.agents/skills/chat-preview/`（シンボリックリンク）から同じ本体を参照する。資産（Node/シェルスクリプト・ハブの殻）は `assets/` に同梱。リポジトリ側にコピーを置かない（2026-10-08 に ATS リポジトリ同梱版を廃止して統合済み）。

## いつ出すか（自動判定・2026-10-08 改定）

これまでは「テキストで答える → ユーザーが `/chat-preview` を打つ」の2往復が最多だった（直近1か月で引数なし起動 174 回。追加指示は「ビフォーアフターをモックかスクショで」「もっと図解とか使って」「進捗をプレビューで」に集中）。**この往復をなくす。** 回答を書く前に内容タイプを判定し、下表のどれかに当たるなら**同じターンで**「短いテキスト（結論と判断材料）＋プレビュー」を出す。ユーザーが何も言わなくても出す。

| 内容タイプ | 判定の手がかり | 必ず付ける形（省略不可） |
|---|---|---|
| **UI の変更・修正案・画面の説明** | 画面・コンポーネント・レイアウト・文言・導線の話。PR の UI 差分の報告 | **Before/After を横並び**（`.grid2`）。現状＝実画面スクショ or 既存UIを再現したモック、提案＝モック。**赤ペン番号**で差分を指し、`references/ui-preview.md` に従う。文章やフロー図だけで代用しない |
| **進捗・完了報告・残タスク** | 「どこまで終わったか」「次に何をするか」「PR の現在地」 | `.ck` チェックリスト（done/todo/blocked）＋ 棒・タイムライン（`.bar`/`.track`）。前回のステップがあれば差分を明示 |
| **設計・アーキテクチャ・処理やデータの流れ** | 仕組み・構成・トリガーと動き・状態遷移 | フロー図（`.flow` or Mermaid）。変更を伴うなら「現状」と「理想」の2図を並べる |
| **調査結果・原因分析・複数案の比較・レビュー結果** | 調べたこと、原因、案 A/B/C、リスク | `<table>` で軸をそろえた比較。リスクは危険度×発生可能性の5段階。最後に `.decide` で推奨つき選択肢を1つ |
| **商談・営業向け資料** | 企業調査、提案構成、追客メモ | 固定フォーマットの表。1画面に収める |

**出さないもの**：1〜2行で済む回答、コマンドを実行しただけの報告、「続けて」「OK」への短い応答、同じステップの軽微な訂正（この場合は既存タブを上書き更新する）。迷ったら「ユーザーがこのあと『図解して』と言いそうか」で判断し、言いそうなら出す。

**ユーザーが明示した見せ方は上書き優先**（「モックで」「スクショで」「いつもの棒で」「Mermaid で」と言われたらその形にする。別の形に置き換えない）。

## 誰が作るか（モデルの軽量化）

プレビューの HTML 作成は軽量モデルで足りる。調査・設計・判断は本体モデルが行い、**このスキルが起動したあとの「HTML 組み立て → 登録 → 表示」は軽量モデルが担当する**。

- **Claude Code**: frontmatter の `model: haiku` により、このスキルを起動したターンは会話文脈を保ったまま最新 Haiku（2026-10 時点 Haiku 5.5）で実行される。設定は保存されず、次のターンは元のモデルに戻る。
- **Codex**: このスキルを使うときは、本体で判断材料を整理したうえで、**`spawn_agent`（`model: "gpt-6-luna"`、`fork_context: true`）にプレビュー作成を委任**する。委任メッセージには「描く内容の要点」「内容タイプと必ず付ける形」「ハブ slug・KEY・TITLE」「この SKILL.md のパス」を含める。Luna 子エージェントが手順 2〜7 を実行し、HUB_URL を返す。本体はそのリンクをユーザーに貼る。

軽量モデルで品質が足りないのは「実画面スクショの撮影」と「操作可能モックの設計」のみ。これらは本体モデルが先に素材（スクショの data URI、モックの構造）を用意してから委任する。

## ハブとタブの運用モデル

- **ハブは worktree/プロジェクトごとに1つ**。場所は `~/.claude/chat-preview-<project-slug>/hub.html`（`CHAT_PREVIEW_BASE` 環境変数で指定）。**異なる worktree/セッションの内容を同じハブに混ぜない**。
- **ハブ内のサイドバータブ＝同じ話の進捗ステップ**（例: ①完成報告 ②アーキテクチャ ③調査結果）。新しいステップは**新しいタブとして追加**し、既存ステップの改訂だけ同じタブを上書きする。
- `<project-slug>` は**内容が属するリポジトリ**から決める（セッションの cwd ではない。ATS のツリーからサイドプロジェクトの話をしている場合はサイドプロジェクト側）。
- Chromeタブはハブ単位で1つ。同じハブの更新では新規タブを開かず再利用する。
- 古いタブは `register-tab.js` が自動で間引く（直近 8 件は常に保持、それ以外は 14 日超で削除、総数 40 件まで）。手動の掃除は不要。
- 旧・共有ハブ（`~/.claude/chat-preview/hub.html`）は過去分の閲覧用。**新規の書き込みは禁止**。

## 動作（手順）

1. **何を描くかを決める**：上の判定表で内容タイプを決め、「必ず付ける形」を確定する。題材は直前の自分の説明。ユーザーが「これを」と指したらそれ。
   UI を含む場合は [モック・スクショ・赤ペン・操作比較の手順](references/ui-preview.md) を読む。対象の既存画面やモックを確認し、利用場面に沿って何を見せるか決める。
2. **assets/hub-template.html の <style> を参照する**：コンポーネントCSS（`.card` `.grid2` `.flow` `.ck` `.decide` `.kv` 等）はハブ側にすでに入っている。作るのは `<body>` に入る**HTMLフラグメントのみ**（`<!doctype>` `<head>` 等は書かない。`<h1>` から書き始める）。
3. **ハブ（プロジェクト）とタブ（進捗ステップ）を決める**：
   - **ハブ**: 内容が属するプロジェクトのリポジトリ名から slug を決め（例: `ai-secretary-avatar`）、`CHAT_PREVIEW_BASE="$HOME/.claude/chat-preview-<slug>"` とする。ブランチ/worktree で話が分かれるなら slug にブランチを含めてよい
   - **タブ KEY**: 同じ話の何ステップ目かを表す連番＋短い slug（例: `01-kanseihoukoku`, `02-architecture`）。**新しい話題ステップ→新しい KEY（タブ追加）**、**既存ステップの改訂→同じ KEY（上書き）**。追加前に `$CHAT_PREVIEW_BASE/data/index.js` で既存 KEY を確認する
   - **TITLE**: サイドバーに出る日本語の短い見出し（例: `① 完成報告`）
   ```bash
   CHAT_PREVIEW_BASE="$HOME/.claude/chat-preview-<slug>"
   ASSETS="$HOME/.claude/skills/chat-preview/assets"
   ```
4. **HTMLフラグメントを一時ファイルに書く**：下記コンポーネントで本文を組み立て、スクラッチパッド配下の `content.html` に保存する。登録用に本文全体をエスケープする必要はない（次の手順が base64 で安全に運ぶ）。HTMLのテキスト・属性値や `iframe srcdoc` は通常どおりエスケープする。**内容は簡潔に**：1タブの本文が 300KB を超えると登録時に `warning` が返る。長大な内容は要点に絞るか複数タブ（別 KEY）に分ける。
5. **登録する**（bash 1発。`CHAT_PREVIEW_BASE` を必ず付ける）：
   ```bash
   REGISTER_OUT="$(CHAT_PREVIEW_BASE="$CHAT_PREVIEW_BASE" node "$ASSETS/register-tab.js" \
     --key "$KEY" --title "$TITLE" --cwd "<プロジェクトのルート>" --html-file /path/to/content.html)"
   echo "$REGISTER_OUT"
   ```
   `$CHAT_PREVIEW_BASE/data/<KEY>.js` と `data/index.js` を更新し、`hub.html` の殻も最新化する。**同じハブの他のステップには触れない**。標準出力は `{"ok":true,...,"url":"file://.../hub.html#<KEY>","tabCount":N,"evictedCount":N,"warning"?:"..."}`。`warning` が付いたら本文を分割・要約する。
6. **ハブを開く/前面化する**（bash 1発）：
   ```bash
   HUB_URL="$(CHAT_PREVIEW_BASE="$CHAT_PREVIEW_BASE" "$ASSETS/open-hub.sh" "$KEY")"
   ```
   Chrome にこのハブのタブがあれば再利用して該当ステップにジャンプし、重複タブは閉じる。無ければ1つだけ新規タブを開く。初回のみ macOS のオートメーション権限を聞かれることがある。**成功・失敗どちらでも最後の1行に `HUB_URL`（`file://...#KEY`）が出る**ので、自動オープンが失敗しても手動で開けるリンクが必ず手に入る。
7. **表示を確認する**：画像・モック・注釈を含む場合はブラウザで読めることと注釈の位置を確認し、操作比較は両案の同じ操作を試す。
8. **報告する**：「Chat Preview（<プロジェクト名>）のサイドバーに『{TITLE}』を追加/更新しました」と一言添え、**続けて必ず `HUB_URL` をそのままチャットに貼る**（自動で開いたかに関わらず毎回。Chrome 操作は権限やウィンドウ状態に左右され、成功したように見えて反映されないことがある）。調整希望があれば手順4〜7をやり直す（同じ `KEY` で上書き）。

**やってはいけないこと**：
- プロジェクトディレクトリへ直接 `chat-preview.html` を書いて `open` する（旧方式）。必ず `register-tab.js` → `open-hub.sh` の経路を使う
- **`CHAT_PREVIEW_BASE` を付けずに共有ハブ（`~/.claude/chat-preview/`）へ書き込む**（他セッションのタブと混ざる・上書き事故の原因。2026-07-14 に実際に発生）
- 別の話題を既存タブに上書きする（新しいステップは新しい KEY で追加する）
- UI の話をフロー図や文章だけで済ませる（Before/After モックが必須）

## 何より大事なこと（なぜ図解するのか）

ユーザーがこのスキルを呼ぶのは「**チャットの説明が頭に入りにくい**」とき。だから——

**関数名・クラス名・専門用語を極力出さない**。出すなら役割を平易に言い換える（例：「buildQuerySpecFromMessage」→「質問を集計の指示書に変換する処理」）。**例外**：ユーザーが「どう実装したか／どの変更で実現したか」を求めたら、後述の「実装の対応づけ」で関数名・ファイル・コミットを出してよい（その場合も平易な説明とペアで）。
**冒頭に一言まとめ**（.lead か先頭の .card）。「結局何の話か」を最初の1〜2文で。
**内容に合った図を選ぶ**（下記）。文章をただ HTML 化するのではなく、構造を図に落とす。
**ユーザーに判断してほしいことがあれば最後に1つだけ目立たせる**（.decide）。確認項目が多すぎると読まれない。

## UIの説明は画面を見ながら理解できる形にする

UIに関する説明では、**文章だけで終わらず、既存UIに沿ったモックまたは実画面スクショを使う**。見るべき場所は赤い枠・矢印・番号で指し、短い説明を対応させる。実画面・現状の再現・未実装の提案は区別する。

- 現状と理想、現行案と提案は同じ題材・条件で並べるか切り替える。
- 操作体験を比べるときは、両案とも同じ入力・開始操作から結果まで試せるようにする。
- 「元のモックを修正して」ならその成果物に追記する。比較のときは現行案も残す。
- 「staging の今と PR の比較」だけで終わらせず、「どう変更したいのか（理想）」まで入れる（過去に指摘あり）。
- 説明の題材にUIがなければ、通常の図解を使う。

素材の選び方、赤ペンの置き方、操作モックの実装・検証は [references/ui-preview.md](references/ui-preview.md) を参照する。

### フロー比較・状態遷移・依存関係（Mermaid）
前後フローの比較・状態遷移・複数要素の関係は **Mermaid** が読みやすい。<pre class="mermaid">…</pre> に DSL を書くだけでよい——**描画スクリプトを自分で足す必要はない**。ハブ側が `.mermaid` 要素の有無を見て、必要な時だけ Mermaid の CDN module を動的に読み込む（オフライン時や未使用時はネットアクセスしない）。
前後比較は subgraph BEFORE[...] / subgraph AFTER[...] の2ブロック＋classDef bad/ok の色分けが一目で分かる（赤=問題ルート、緑=正ルート）。ノード内改行は <br/>、絵文字は &#128683; 等の実体参照。**分岐の“合流先”で良し悪しが分かるように描く**。**Mermaid を使ったら同じ DSL をチャットにも
mermaid コードブロックで出す**（GitHub PR・Notion・mermaid.live にそのまま貼れて再利用できる）。
html
<pre class="mermaid">
flowchart TB

    Q1["質問"] --> M1{"条件拾えた?"}
    M1 -- 不明 --> G1["無視→全件"] --> R1["誤答"]
  end
  subgraph AFTER["後 : 指示書＋fail-closed"]
    Q2["質問"] --> S2["指示書へ翻訳"] --> C2{"知らない条件?"}
    C2 -- あり --> K2["集計せず確認"]
    C2 -- なし --> E2["実在条件だけ集計"] --> R2["正答"]
  end
  classDef bad fill:#fee2e2,stroke:#fca5a5,color:#b91c1c;
  classDef ok fill:#dcfce7,stroke:#86efac,color:#15803d;
  class G1,R1 bad
  class K2,E2,R2 ok
</pre>

### 実装の対応づけ（挙動 → コード）— 「どう実装したか」を聞かれたら
「どの変更で実現したか」「どう実装したか」を求められたら、`<table>` で **挙動 → 中心の仕組み（関数）→ 主なファイル → コミット** を1対1に並べる。関数名・ファイルは `<code>`/`.ex` で出してよいが、**必ず平易な説明とペア**にする。コミットは増分単位で短ハッシュ＋（増分N）。さらに掘るなら「肝の判定ロジックを3ステップ `.flow`」「擬似コード `.kv`」も足す。
html
<table>
  <tr><th>実現したこと</th><th>中心の仕組み（関数）</th><th>主なファイル</th><th>コミット</th></tr>
  <tr><td>前段の門番</td><td><code>run()</code> で先に解決 → <code>buildUnsupportedQueryResponse()</code></td><td><span class="ex">ai-chat-orchestrator.ts</span></td><td>7776aca7</td></tr>
</table>

### 補足
強調なしの注記は .note、コード片・パスは .ex。色付きの語句強調は .badtag/.oktag/.warntag。.kv は擬似コード/構造の暗色表示。タブ内メモ（`data-memo`）は目視チェック表などユーザーが書き込む用途に使える。

## 詳しさのレベル（PR・変更の解説向け）

「PR の変化を見せて」「もっと詳しく」「どう実装したか」と**段階的に深掘り**を求められることが多い。1枚に次の順で積むと追従しやすい：

1. **一言まとめ**（.lead）→ 2. **前後フロー**（2カラム or Mermaid）→ 3. **具体例の前後**（<table>）→ 4. **なぜこの設計か（採用/却下）**（.col-ok/.col-bad）→ 5. **実装の対応づけ**（挙動→関数→ファイル→コミット）→ 6. **次の一手・残課題**（.col-warn か .decide）。

最初は 1〜3 で出し、「もっと詳しく」で 4、「どう実装したか」で 5 を足す、という**増分更新**でよい（同じ `KEY` で手順4〜7をやり直せば、同じタブが上書きされる）。

## 守ること

**自己完結（既定）**：CDN・外部 CSS/JS・画像 URL を使わない。画像はdata URI、モックはローカルで完結するHTML/CSS/JSとして組み込む。追加CSSはタブ内に限定する。オフラインでも開ける。**唯一の例外は Mermaid**：`.mermaid` を使った時だけハブが自動でCDN moduleを読みに行く（ネット接続が要る旨を .note で明記し、同じ DSL をチャットにも出す）。
**日本語**・読み手は急いでいる前提で簡潔に。1ページに詰め込みすぎない（節は <h2> で区切る）。
図が内容に合わない時は無理に全部使わず、合うものだけ選ぶ。新しい見せ方が要るなら `assets/hub-template.html` の `<style>` に少量足してよい（自己完結は維持。全ハブに影響する共有シェルなので変更は控えめに）。
**worktree/プロジェクトを跨いで上書きしない**：手順3の通り、ハブは対象プロジェクト・worktree別、`KEY` はそのハブ内の進捗ステップ別にする。

## 例（トリガー → 動作）

**Input:** ユーザー「この PR で応募者詳細の右カラムをどう変えた？」（明示トリガーなし）
**Output:** 内容タイプ＝UI変更と判定。テキストで結論を2〜3行書いたあと、同じターンでこのスキルを起動。staging の現画面スクショ（取れなければ再現モック）と PR 後のモックを `.grid2` で横並びにし、赤ペン番号で差分を指す。ハブに登録し、報告と HUB_URL を貼る。

**Input:** ユーザー「いまの説明、/chat-preview で見せて」
**Output:** 直前の説明を題材に、一言まとめ＋内容に合う図のHTMLフラグメントを作り、`register-tab.js` で登録、`open-hub.sh` でハブタブを前面化してから報告と HUB_URL。

**Input:** 「現状と理想を、モックやスクショに赤ペンを入れて比較して」
**Output:** 同じ利用場面の実画面と提案モックを並べ、差分を番号付きの赤ペンで説明する。素材の種別と提案の未実装範囲を明記し、ハブに登録して表示を確認する。

**Input:** 「元のモックを修正して」「AもBも同じ送信から体験したい」
**Output:** 既存成果物を更新し、両案で同じ入力・開始状態・送信操作を用意する。提案表示・確認・確定／取消までの差を試せるようにし、赤ペンで注目点を示す。

**Input:** 「マージOK」「続けて」
**Output:** プレビューは出さない（短い応答）。作業が区切りに達して進捗を報告するタイミングで、進捗タイプとして出す。

## 配布と更新（チーム向け）

配布元は GitHub `miuit-products/claude-code-starter-kit` の `.claude/skills/chat-preview/`。メンバーは Mac で一度だけ次を実行すると、`~/.claude/skills`（Claude Code）と `~/.agents/skills`（Codex）の両方に入る。

```bash
skillshare install miuit-products/claude-code-starter-kit/.claude/skills/chat-preview
```

更新は `skillshare install miuit-products/claude-code-starter-kit/.claude/skills/chat-preview --update`。スキルを直したら starter-kit へ PR を出して配る。macOS の Chrome 前提（AppleScript でタブを操作する）。
