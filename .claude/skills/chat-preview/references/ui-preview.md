# UIをモック・スクショ・赤ペンで説明する

UIの説明・改善提案・変更報告では、読み手が「どの画面で、何をして、どう変わるか」を見て判断できる形にする。以下は会話ログで繰り返された希望を手順化したもの。毎回すべてを盛り込むのではなく、説明したい差分に合わせて選ぶ。

## 見せ方を選ぶ

| 説明したいこと | 主な見せ方 |
|---|---|
| 現在の画面・実装済みの変化 | 実画面のスクショ＋注釈 |
| 未実装のUI・改善案 | 既存UIに沿ったHTML/CSSモック＋注釈 |
| 現状と理想、現行案と提案 | 同じ題材のBefore/AfterまたはA/B比較 |
| 操作手順、編集・送信後の挙動 | 操作可能なモック。静止画なら状態を順番に並べる |
| 選択肢を広げたい | 判断軸が異なる複数案。指定数があればそれに従う |

「モックで」「スクショを使って」「赤ペンで」「体験を比較したい」と指定された場合は、その表現を成果物に入れる。文章や抽象的なフローだけに置き換えない。UIのない話は通常の図解でよい。

## 既存の画面を基準にする

- 対象画面・既存モック・デザインシステムを先に確認する。レイアウト、色、見出し、ボタン名、情報の粒度を引き継ぎ、提案の差分が見えるようにする。
- モックはHTML/CSSで画面構造を表す。ラベルや操作を正確に比較したいUIを、生成画像だけで代用しない。
- 「元のモックを修正して」なら元の成果物を更新する。比較を求められた場合は現行案を比較対象として保持し、提案だけで置き換えない。
- 「誰が・どんな場面で・何をしたいか」を短いユースケースにする。画面のそばに「ここを押す→この表示になる→利用者に何がうれしいか」を添える。
- 新しい話の比較は新しいハブ内タブに追加し、その比較への補足・赤ペン追加は同じタブを更新する。ハブとKEYはSKILL.mdの手順3に従う。

## スクショを根拠として扱う

- 利用できるブラウザ操作・スクリーンショット取得ツールで対象画面を確認して撮影する。既存画像を使う場合も実際に開いて確認する。
- 「実画面（ローカル／stagingなど）」「現状の再現モック」「提案モック・未実装」をそれぞれ明記する。実画面を取得できない場合は、その理由と再現の限界を添える。
- 現状を示すスクショと、提案を示すモックを並べてよい。ただし素材の種別を明示し、モックを実装・動作確認の証拠にしない。
- 比較対象の表示幅・拡大率・表示範囲をそろえる。読めない全画面の縮小画像だけで済ませず、必要箇所の拡大図を添える。
- プレビューには必要箇所だけを掲載し、認証情報・個人情報を含めない。撮影に実操作が必要でも、プレビュー作成の依頼を実データの送信・変更の許可と解釈しない。
- 画像は原則としてdata URIで埋め込み、元の一時ファイルを消しても表示できるようにする。大きさや解像度を調整して文字の可読性を保つ。スクラッチパッドの絶対パスや一時サーバーに画像表示を依存させない。

## 赤ペンは画面上の対象と説明を結び付ける

- 対象を赤い枠・丸・下線・矢印で指し、①②③などの番号と短い説明を対応させる。赤文字の説明文を画面の下に並べるだけで済ませない。
- 注釈は「場所」だけでなく「操作」「変更点」「理由・影響」のいずれかを伝える。例：`② 修正する → この質問だけを編集。ほかの質問は保持`。
- 1画面で追える少数の注釈に絞る。文字やボタンを覆わず、説明が増える場合は画面・ステップを分ける。
- 赤は注釈の色として使い、必ずしもエラーを意味しない。問題、提案、確認済みの違いは文言でも示す。
- 元画像を保持し、HTML/CSSまたはインラインSVGを別レイヤーとして重ねる。画像なら元画像の比率と座標系を合わせ、モックなら対象要素を基準に配置する。ウィンドウ幅を変えても矢印と対象がずれないようにする。
- 操作するモックでは注釈レイヤーがクリックを妨げないようにする。注釈が多い場合は表示切替を用意し、注釈なしでも操作を試せるようにする。

## 比較は同じ操作で差が分かるようにする

- 左に現状、右に提案、またはA/B切替を使う。同じ利用者・題材・データ・開始状態・入力文を使い、変更した軸が分かるようにする。
- 片方は送信前、もう片方は完成後、のような不公平な比較を避ける。体験比較なら両方に同じ入口を用意する。
- 例：A/Bともに同じ修正依頼を入力して「送信」から始める。Aは即座に変更案を表示、Bは意図を確認してから変更案を表示する。確認の手間と安心感の違いを、両方操作して判断できるようにする。
- 編集なら「開始→編集／送信→変更前後の確認→確定／取消」まで、比較に必要な状態を実装する。「同じ例をもう一度試す」で開始状態へ戻せると比較しやすい。
- A/Bの操作状態を独立させ、一方の操作が他方の開始状態を壊さないようにする。
- 見た目の好みだけでなく、操作数、迷いやすさ、変更対象・影響の見え方、元に戻せるか等、今回の論点に合う観点を短く添える。推奨理由と残る懸念も示す。
- 案数指定がなければ必要な数に絞る。複数案を求められた場合は、配色違いだけでなく情報配置・導線・確認方法などの違いを作る。

## ハブへ組み込むときの注意

- 静的なモック、画像、赤ペンは通常のHTMLフラグメントに含める。追加CSSはタブ固有のルートID配下に限定し、共通の `.card` や `button` を一括で上書きしない。
- 現行ハブはフラグメントを `innerHTML` で挿入するため、フラグメント内の `<script>` が実行される前提にしない。
- 操作可能なモックにJavaScriptが必要なら、ハブ内の `iframe srcdoc` にCSS/JSを含む独立文書を入れる方法を使える。属性値は機械的にHTMLエスケープし、`sandbox="allow-scripts"` で親ハブから分離する。高さを十分に確保し、フレーム内でも入力・比較対象を読めるようにする。
- モックの操作はローカルのサンプルデータで完結させる。固定の回答・模擬動作はその旨を表示し、実APIや実データへの保存は接続しない。
- ユーザーが特定の既存成果物や出力先を指定した場合はその指示を優先する。今回の見せ方を追加したこと自体を、外部公開や既存共有先の更新の許可にはしない。

## 出す前の確認

実際にブラウザで開き、画像が読み込めること、文字の読みやすさ、注釈の位置、画面幅を変えたときの欠け・重なりを確認する。操作可能なモックは比較対象それぞれで主要操作と取消・再試行を試す。

「実画面」「提案」「固定サンプル」の表示を確認し、実装していない機能や検証していない挙動を完成扱いしない。ブラウザで確認できなかった部分は、完了報告で区別する。
